# Capa Silver

## Introducción

La capa Silver transforma los datos recibidos en Bronze en tablas consistentes
para las capas Gold y de reporting. Su responsabilidad es limpiar valores,
normalizar nombres, aplicar tipos, seleccionar columnas del contrato, eliminar
duplicados y validar las claves primarias y el número mínimo de filas.

Bronze conserva la extracción y sus snapshots; Silver conserva una versión
estructurada, tipada y trazable. El contrato de cada fuente vive en
`07_config/mappings.yaml`: `source_name` identifica la columna de entrada,
`target_name` su nombre normalizado, `dtype` su tipo, `required` indica si es
obligatoria, `primary_key` identifica columnas de clave y `min_rows` fija el
mínimo de filas aceptable. `07_config/sources.yaml` complementa ese contrato
con el tipo de fuente, ruta, patrón, frecuencia, sistema y responsable.

La implementación reutilizable está en
`utils/transformers_silver.py` (la ruta histórica `02_silver/utils/transformers.py`
no existe en esta versión). Los scripts `clean_*.py` importan estas funciones
en lugar de reimplementar el flujo común. Las excepciones son las fuentes
semiestructuradas y `9_1_cartera_kits_clean.py`, que requieren extracción
específica antes de poder escribir Silver.

> **Conteo del orquestador:** `pipeline.py` contiene 21 entradas en
> `SILVER_SCRIPTS`, aunque la documentación solicitada las denomina 20. Se
> documentan las 21 entradas para mantener la página alineada con el código.

## Reglas generales de transformación

### Flujo de `prepare_silver_frame`

Para las fuentes estructuradas, el flujo estándar es:

1. `build_rename_map()` construye `source_name -> target_name` y se renombran
	 las columnas.
2. Se conservan únicamente las columnas declaradas en `columns` del contrato.
3. `apply_dtypes()` aplica el `dtype_map`.
4. Se valida que las columnas `required` estén presentes. Por defecto se
	 registran sus nulos; si el script activa `drop_required_nulls`, también se
	 eliminan esas filas.
5. Se eliminan nulos en `dropna_subset` cuando el script define una regla de
	 negocio específica.
6. Se deduplica usando `dedup_subset` cuando se proporciona.
7. Se valida la PK: se eliminan filas con nulos en las columnas presentes de
	 la PK y se conserva la primera ocurrencia duplicada.
8. Se valida `min_rows`; si el resultado queda por debajo del mínimo, la fuente
	 falla.

`build_dtype_map()` construye el mapa desde el contrato y
`load_contract_from_mappings()` carga la entrada de `mappings.yaml`. La
escritura estándar usa Parquet, PyArrow y compresión Snappy; cuando se usa
`write_silver_parquet()` se agrega `fuente_bronce` con el nombre del snapshot.

### Tipos soportados

| `dtype` | Tratamiento en `apply_dtypes()` |
|---|---|
| `string` | `clean_string()`: convierte a texto, aplica `strip` y transforma vacíos, `nan` y `None` en nulos. |
| `integer` | `to_numeric(..., dtype="Int64")`, con coerción segura. |
| `float` | `to_numeric(..., dtype="float")`; elimina caracteres no numéricos, excepto punto y signo. |
| `date` | `pd.to_datetime(..., errors="coerce").dt.date`. `to_date()` ofrece la misma conversión reutilizable con formato opcional. |
| `datetime` | `pd.to_datetime(..., errors="coerce", dayfirst=True)`. |

Un `dtype` no reconocido se registra como advertencia y se trata como
`string`. Por ello, aunque `4_2_invoices_vigigas` declara `time`, la función
común no tiene una rama `time` y deja esa columna como texto.

### Snapshots y selección de versiones

`find_parquet_files()` busca los Parquet de Bronze y los ordena por fecha de
modificación. `select_latest_per_source()` agrupa los nombres con la
convención:

```text
<nombre>__<timestamp>.parquet
```

El timestamp esperado es `%Y-%m-%dT%H-%M-%S`. Por cada nombre lógico se usa el
timestamp más reciente y se descartan las versiones anteriores sin procesar.
Si el nombre no contiene `__`, el archivo se trata como grupo propio y se usa
su fecha de modificación; si el timestamp no se puede interpretar, también se
usa esa fecha como respaldo. `build_silver_filename()` elimina el sufijo de
snapshot al generar el nombre de salida.

### Logging

`configure_silver_logger()` intenta usar `utils/logger.py`, conserva el nombre
del logger y crea el archivo de log en `09_logs/02_silver`. Si esa utilidad no
está disponible, usa `logging.basicConfig()` con nivel `INFO` y el formato
estándar del proyecto, y deja una advertencia. `log_silver_summary()` registra
forma, tipos, nulos y las tres primeras filas. Algunos scripts todavía
reproducen ese bloque directamente, pero el resultado es equivalente.

opcional y `PK` identifica una columna marcada como `primary_key: true` en el
elemento de `columns`. La PK de nivel de fuente se indica después de la tabla
cuando existe.

## Fuentes semiestructuradas (caso especial)

En `mappings.yaml`, `3_3_almacenamiento_control_diario`,
`5_3_ventas_marketing`, `6_1_cartera_producto` y `9_1_creditos_kits` tienen
`semiestructurada: true`, `status: pendiente_diseno`, `columns: []`, PK nula y
`min_rows: null`. No se define todavía un contrato de columnas porque los
Excel usan celdas combinadas, varias tablas por hoja, encabezados irregulares
o una hoja por vehículo; el aplanado automático de Bronze no produce un
esquema determinístico.

`3_3` sí tiene una solución ad-hoc completa: recupera el Excel crudo, detecta
hojas por mes, escanea bloques `ENTRADA`/`SALIDA` y genera salidas separadas
para control diario y reporte mensual. `6_1` también tiene solución ad-hoc:
